# TCP 与 TLS 检查实施计划

范围来自已确认建设方案的“网络服务检查”和首批主动检查。复用现有网络目标、管理员批准、冻结范围、模板校验、扫描计划和逐项结果；自研 Go 执行，不调用外部扫描程序。以下能力已实现并通过隔离验收；部署状态与明确限制记录在文末。

## 对使用者的实际含义

- TCP 连接检查说明指定服务是否能够建立连接；端口可达本身不产生“已确认漏洞”。只读服务特征检查保留服务主动发来的有限字节，不发送任意命令、不认证、不扫描端口段。
- TLS 检查与 HTTPS 内容检查分开。前者检查实际握手、公开证书、有效期和协商结果；后者继续严格验证证书后读取 HTTP 响应，不会为此增加跳过验证的开关。
- 只有实际结果满足已批准的风险条件时生成发现。例如，实际接收的证书在检查时间已经过期。连接失败、握手未完成或证据不足分别显示原因，不能算“检查通过”。
- 未协商到某个旧版本不等于证明服务不支持所有弱协议；只能报告本次明确客户端条件下的结果。

## 修改边界

1. **网络目标与批准范围**：协议增加 TCP、TLS。TCP/TLS只批准明确主机、解析地址和单个端口，不借用无意义的Web路径字段。修改协议、端口、地址或信任条件会撤销原范围批准。现有HTTP目标的序列化和摘要保持兼容，不自动改变既有批准。
2. **模板与条件**：新增明确的本地网络检查类型，有限枚举条件和业务提示。连接观察、只读服务特征、证书有效期与明确TLS条件分别展示；只读人员不能发起或批准。正反样本检查仍先于管理员批准。已有HTTP模板继续按现有契约执行。
3. **Go执行器**：复用固定DNS地址、连接前复核、控制面/元数据地址拒绝及按次预算申请。每次真实连接都取得持久共享额度；沿用3秒连接超时、明确任务截止、有限读取和取消，不能退回进程内独立限速。
4. **TLS公开依据**：保留实际连接方向、检查时间、协商版本/套件、公开证书摘要与有效期。诊断握手观察和证书验证结论分别记录。信任根变化必须可追溯，不能把内部CA未提供误称为已成功利用。
5. **计划与恢复**：继续固定本次端点、规则、来源及批准摘要。停止目标、撤销模板、取消计划、过期租约和负责人失权都阻止后续连接及旧结果提交。恢复保留已用额度，不因API重启重新获得300次预算。
6. **真实问题内容**：风险详情从对应的已完成检查恢复实际公开证据。扫描节点到服务的连接标注为“扫描实际连接”，不画成攻击者链路。未完成记录保留原原因，正常端口观察不混入已确认风险。
7. **界面**：沿用浅色AntD与32px工作区基础间距、15条分页。协议、检查类型与版本使用选择；证书有效期阈值有明确单位和业务说明。详情与预检保持页内交互，不叠加确认弹窗。

## 验证顺序

1. 先增加范围、模板与样本的失败回归；尤其检查旧HTTP批准摘要不变、协议混用被拒绝、空范围和非授权端口不能执行。
2. 使用自建TCP/TLS服务测试真实连接、主动发送的协议特征、有效/过期证书、错误名称、指定信任根、失败握手和超时；仅访问明确受控的测试网络。
3. 通过相同的数据库共享许可验证每次连接计数、全局并发、同目标间隔、取消/撤权、DNS变化和持久恢复；不得以直接调用匹配函数替代该项。
4. 用真实独立进程验证API硬终止、自然租约过期后的恢复与去重，检查没有重新领取额度、重复制造风险或接纳旧结果。
5. 通过HTTP接口和五种分辨率复验创建、预检、批准、计划、逐项结果、风险详情及菜单定位。
6. 更新验收矩阵和操作指南，分别报告已经实现的协议、匹配条件与仍未支持的外部模板语法。
