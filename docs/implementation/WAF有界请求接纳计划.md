# WAF 短时积压与正文内存边界

当前仍保持正式运行门槛关闭。独立长测的受保护快照（waf-persistent-8RpxAT/reports/pool-mid-run.json）记录累计524次队列拒绝；最后几次拒绝时，三个工作进程均已就绪且正在执行，其中一项已占用438ms。这不支持把全部失败归因于冷启动，不能盲目提高每进程64次事务上限或工作进程数量。

先建立两个失败回归：三个真实工作进程短时占用时，32项有限请求应在现有2秒期限内等待并实际完成规则检查；正文读取前，应限制完整在途检查请求，超过上限不读取和分配正文，并保存明确的检查未完成记录。

候选设计为最多64个完整在途检查请求及64项检查等待/执行预算。原24项仅能覆盖100RPS约240ms的积压，低于已经明确的2秒请求检查期限；64项用于覆盖约0.6秒的短时波动，不增加任何执行工作进程。HTTP接纳门在读取正文前取得，并持续覆盖规则、转发与持久访问记录，不把等待请求搬到无界goroutine队列。结束时关闭并释放正文引用，再释放接纳名额。

64是有限内存和等待预算，不是新的通过标准：单个正文仍保持既有1MiB默认值和8MiB配置上限；另按每个站点配置的正文最大值预留共享64MiB预算，8MiB站点最多同时接纳8项，防止仅限制请求数量却扩大内存风险，执行进程仍最多3个、全局管理预留仍保持4进程硬上限，每工作进程64次事务、单次2秒截止、原生计算和内存限制保持。队列满、截止或取消仍明确失败，不能把未检查请求当作正常转发。最坏正文与编码副本需用实际并发及RSS测试核对，不能只根据4KiB参考负载估计。
