# SelfGuard 有效访问探针

本组件是既有 Agent 的可选附属进程，沿用平台主机身份。基础 Agent 继续采集主机信息和连接摘要；本组件对批准的单个端点持续重组有效访问，独立加密排队并上传请求与响应。创建或启用观察源不会自动修改业务或启动抓取。

## 本地主线

平台：数据安全 → 分类与审计 → 访问行为记录、采集覆盖与探针。主机流量及数据库审计页面均可进入关联记录。正文读取与导出分别授权，普通访问无需先命中规则。

索引不保存 SQL 正文、查询参数、认证秘密或返回值。完整协议字节按最多 256 KiB 分段，包含方向、顺序、捕获时间、长度和 SHA256；二进制响应可以无损下载。最终业务用户没有可信上下文时保持未知。HTTP 错误响应不等同于数据库鉴权失败。

正文按捕获时间滚动保留 7 天。上传、重试和长会话不续期；索引保留及容量在系统管理的存储策略配置。默认索引 100000 条、30 天，正文空间 1 GiB，按密文文件字节及未完成预留计费（包含加密开销和未索引对象，不等同于磁盘分配块或数据库容量），达到配额背压到独立探针队列。生产应按有效访问及响应实测配置容量。正文到期清理始终执行；索引自动清理沿用现有存储开关。原始正文不进入普通备份或心跳。

## 安装与持续运行

1. 主机先安装基础 Agent。在平台选择该主机，为数据库或缓存绑定相应实例，再创建明确的网卡、IP、端口及协议观察源。默认禁用，启用后下载该来源配置。再次下载会轮换来源凭据。
2. 配置私有保存为 `0600`，使用 HTTPS；自建 CA 通过配置中的 `caCertificate` 指定，不关闭校验。安装器核对 `/var/lib/selfguard-agent/identity.json` 的 `assetId`，拒绝把另一个主机的来源装入本机。
3. 校验发行包 SHA256，选择主机架构后执行 `sudo ./selfguard-access-probe --install-config /root/source.json`。安装器验证平台授权及端点快照，生成单独的用户、配置、加密队列、常驻服务和每小时离线到期清理任务。它不重启基础 Agent 或业务系统。
4. 在采集覆盖页检查 RUNNING、最后上报、队列、待上传事件和缺口；返回访问行为页核对真实请求和响应。主机普通流量摘要仍在网络安全的主机与流量页。

常驻服务名为 `selfguard-access-<sourceId>`、`selfguard-access-<sourceId>-capture`；到期清理为相同前缀的 `-expire.timer`。停止两项来源服务即可停止采集，基础 Agent 保留。撤销来源会使旧凭据失效，最迟在下一次配置检查时停止探针。安装文件位于 `/etc/selfguard-probe/<sourceId>`，队列位于 `/var/lib/selfguard/access-probe/<sourceId>`。探针版本可通过 `--version` 查看。

抓取进程只有根维护的端点配置，不持有平台凭据；网络抓取只需要 CAP_NET_RAW。解码和上传运行于专用普通用户，能力集合为空。两者通过私有 FIFO 传递，原包不写临时明文文件。队列和平台证据均使用 AES-GCM；平台按来源、事件、方向、顺序、时间及校验和绑定正文。接口仅在持久化后确认，确认错配不会清理本地字节。

## TLS 观察点

网络旁路不会自动解密 TLS。进程明文模式使用独立的、只读的 OpenSSL uprobe 采集器，不使用 LD_PRELOAD、不导出会话密钥、不接管业务转发。附着库路径、PID、启动标识、UID、程序及运行库 SHA256 均需固定并核验。

在指定 Linux 主机执行 `sudo ./selfguard-access-probe --inspect-process <PID> --library /实际映射/libssl.so.3 > /root/process-profile.json`，将生成的评审信息导入观察源。按组件完成权限、故障和性能评审后，再安装该源配置。程序或运行库变更、进程重启均需重新核验；旧来源可停用，新建评审来源后保留原记录。

该适配器只读取已批准端点的 SSL_read/SSL_write 及 _ex 返回缓冲。内核中先验证 socket 和端点，再读取应用字节。观察从新的 SSL_set_fd/rfd/wfd 绑定开始；自定义 BIO、静态链接、其他 TLS 库、缺少 BTF 或不可附着的组合不代表已覆盖。只支持检查器接受的 64 位小端动态运行库。旧 CentOS 或部分麒麟内核需单独验收，不能因主机 Agent 在线就认定 TLS 正文可读。

每次调用复制预算为 16 KiB，按 100 字节片段输出并重组；大响应由多次调用组成。单次调用超过预算不会伪装完整。超预算、丢失、断开、无法绑定或不支持都会形成缺口。bpftrace 是系统单独安装的运行时，发行包不捆绑它；0.1.4 起在安装和实际附着前要求 `/usr/bin/bpftrace` 版本不低于 0.17.0（观察程序使用该版本开始提供的 `%rh` 输出）。满足版本下限仍需目标内核、库与协议实测，不能视为已认证；旧版使用 BPFTRACE_STRLEN 控制 buf 上限和带空格的十六进制格式，见 [0.17 官方手册](https://github.com/bpftrace/bpftrace/blob/v0.17.0/man/adoc/bpftrace.adoc#environment-variables)。生成的附着程序可用 `--openssl-capture-config /etc/selfguard-probe/<sourceId>/capture.json --review-observer` 进行只读检查。

## 协议验收边界

| 协议 | 实际验证 | 当前边界 |
| --- | --- | --- |
| HTTP/1.1 | 重复真实请求、错误、分块、262144 字节二进制响应、PCAP 重放、持续抓取超过30秒 | HTTP/2、WebSocket 升级、CONNECT 隧道明确不支持；不能推断最终用户 |
| MySQL 8.4.7 | 真实登录、文本查询、重复读取、错误及262144字节返回；0.1.2另验收参数化预编译查询两次执行，原始列定义参与分类，逐字节保留完整请求响应 | 服务器游标、压缩、可选结果元数据及切换用户保持覆盖缺口；其他版本组合独立验收 |
| PostgreSQL 14 | 真实登录、简单查询、重复读取、错误及262144字节返回 | 扩展协议批次标明关联不足；仅有关系OID时不伪造对象映射，分类可能未知 |
| Redis 7.4 | RESP读写、重复读取、错误、262144字节返回及命名空间分类；0.1.2另验收RESP3 HELLO AUTH账号及MSET/MGET多键分类 | 事务排队不等同于提交成功；EXEC及订阅推送的完整关联仍有边界 |
| Oracle、SQL Server、达梦、金仓 | 保留既有原生审计与标准审计接入 | 新探针尚未通过完整线协议验收，显示不支持，不能称已解析原生访问 |
| OpenSSL TLS | Linux ARM64 / 动态 OpenSSL 3 / TLS1.3 / HTTP1.1，真实读取两份262144字节返回、排除未批准端口，停止观察进程后业务继续 | 单次SSL调用上限16KiB；其他内核、架构、库及数据库TLS组合仍需单独验收 |

## 开发验证

在 Linux 下运行 `go test -race ./...`，构建使用 `CGO_ENABLED=0 go build -trimpath .`。捕获组件需要授权的 CAP_NET_RAW；解码器明确拒绝 root 身份。有限 PCAP 重放可使用 `--config 私有配置 --pcap 合成数据.pcap --once`，不代表已完成真实网卡或 TLS 组件验收。

## 交付及恢复

运行 `node scripts/build-access-probe-package.cjs` 生成 Linux amd64/arm64 本地验收包及 SHA256SUMS。该包不含来源凭据、CA私钥、抓包样本或 bpftrace；不属于签名发行升级通道，不会自动下发至主机。ARM64已运行真实链路，amd64仅完成交叉构建时不能当作已验收。

队列为正文和紧急缺口索引分别预留空间。正常事件无法全部保存时保留已持久化前缀并标明缺口；连普通索引也无法保存时写紧急缺口，不能承诺零丢失。重启会将未完成的孤立分段转换为可见恢复缺口后回收，单条永久拒收记录会隔离并保留加密证据，后续正常记录继续上传。页面显示隔离数，需排查后通过受控工具处理，不会自动把拒收记录改写为成功。正常停用、凭据撤销、网络中断和资源上限均不改变业务转发。

持续运行没有30秒自动停止；单条极长响应仍受内存、独立队列、平台配额及七天期限约束，超限明确标明不完整。HTTP2/自定义BIO等未覆盖组合应从已批准的日志、原生审计或另行验收的观察点补充，不能以TCP连接代替完整访问。

## 0.1.2 本地补充验收

MySQL语句关联只保存有界语句ID及操作类型，不把SQL或参数放入索引。关闭及连接重置清理关联；缺失准备上下文标关联不足，切换用户与服务器游标转为不支持，避免套用旧账号/语句。Redis多键按命令的键位置分类，MSET值和认证密码不进入对象索引；HELLO按选项语法消费AUTH与SETNAME。键前缀、参数或对象预算不足明确产生缺口。

本轮在隔离内部网络的MySQL8.4.7、Redis7.4.2上由真实客户端发起访问，经转发记录双向字节并由最终解码器完整还原；未修改业务服务器。Go完整竞态回归另包含这些真实记录。此验收不扩大其他数据库、TLS库、架构/内核及长期运行的既有覆盖声明。0.1.2为本地验收包，未自动发布或安装。

## 0.1.3 对象关联与定级依据

PostgreSQL结果的[RowDescription](https://www.postgresql.org/docs/14/protocol-message-formats.html)提供数据库内的表OID与字段序号；探针保留这些真实编号，不将结果别名或SQL字符串当作原始字段。零编号、无数据库、畸形或超预算元数据明确标记关联缺口。平台需要绑定同一来源实例、数据库的只读元数据快照才能关联列名，快照24小时到期；表结构变化应立即重新导入。表达式、复杂批次、未取得元数据的操作仍不能保证完整对象覆盖。

HTTP可按精确路径和请求方法登记所属实例的分类对象。这属于接口配置关联，不证明该次请求实际调用数据库。平台在访问记录和告警保留关联依据、来源配置版本、分类体系与定义版本、规则原等级和最终等级；普通访问不会仅因数据敏感而自动告警。敏感读取规则填写返回量阈值时，两项条件同时满足才命中。该版本不改变正文七天到期、权限或加密队列机制，也不扩大其他协议/TLS支持声明。


## 0.1.4 运行时前置检查

PostgreSQL 14.24 / Ubuntu 22.04.5 / x86_64 真机只读盘点发现系统仓库提供 bpftrace 0.14.0。原观察程序在其 LLVM 编译阶段触发断言，未附着业务进程；独立合成客户端在校验证书的 TLS1.3 下完成重复查询、262144字节返回和错误查询，不代表探针已经采集这些访问。

新版本在创建用户/服务前及实际附着前检查固定运行时版本，拒绝旧版、缺失、无法执行及无法解析的版本，提供明确诊断；离线生成待评审程序仍不要求安装运行时。新增回归与完整竞态测试通过。版本下限依据 [bpftrace 0.17 官方变更记录](https://github.com/bpftrace/bpftrace/releases/tag/v0.17.0)；本轮没有修改或放宽PID、UID、进程启动身份、运行库摘要及内核端点过滤。

## 0.1.5 旧内核验证复杂度适配

Ubuntu22.04/Linux5.15上的真机对照发现，原每程序21段展开在内核加载阶段失败；相同进程、运行库和端点限制下，7段展开可以加载并回报就绪。新版本将每程序降到7段，增加分片程序数量，仍覆盖单次调用原有16KiB范围；没有缩小字节预算或放宽过滤来取得通过。

生成程序整体超过Linux单参数长度上限，因此实际执行使用root私有0600临时源文件，退出删除。该文件仅含程序，不含应用字节；解码/队列权限隔离不变。对工具输出显式关闭缓冲，静默端点的就绪不再依赖后续业务输出。内核加载、实际字节、平台入库和持续负载仍是独立验收，单程序对照不等于整条链路完成。0.1.5保持本地验收通道，未自动升级原Agent或安装常驻业务探针。

## 0.1.6 末尾分片长度边界

0.1.5完整组实测在最后的部分分片被5.15内核拒绝：LLVM优化消除了内核验证器所需的长度边界。直接添加掩码仍被优化，因此新候选在0..100字节限长后，经线程独立的临时map读取并掩码，再立即删除该条目。字节预算与身份、端点限制不变。原末尾分片失败、修正分片就绪的最小对照已完成；完整组、双向字节一致性及持续运行须分别验证，不凭局部结果认定生产接入完成。
