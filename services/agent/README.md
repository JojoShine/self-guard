# Self Guard Agent

Go 1.25 or later, standard library only (release builds pin Go 1.27.3). Run `go test -race ./...`, then `go build .`.

Set AGENT_SERVER (origin without /api), AGENT_ENROLLMENT_TOKEN, AGENT_STATE_DIR (private persistent directory). AGENT_ALLOWED_ROOT enables permission remediation only inside that directory; default disables remediation. HTTPS is required outside loopback unless AGENT_DEVELOPMENT=true. Optional AGENT_CONFIG JSON overrides environment values using Config field names; Checks is an array of {"Path":"/absolute/file","Mode":"0600"}. Do not put tokens in source control.

30-second cycles enroll once, send bounded inventory and up to 100 permission observations, claim approved tasks, and report outcomes. Reports are durably buffered (128 reports, max 1 MiB each); full storage stops work rather than silently dropping reports. Identity, task history and queue files use mode 0600. Task history caps at 10,000 and fails closed. A persisted execution marker prevents executing a claimed task twice after a crash; interrupted tasks require manual review. Success requires independent server verification and does not close findings.

FILE_PERMISSION and the constrained CONFIG_VALUE template described below operate on regular files. Symlink components are refused and chmod operates on an opened descriptor with identity checks. Allowed directories must not be writable by untrusted users. Linux uses secure descriptor traversal; other platforms disable remediation. Previous permission mode is recorded, with rollback on verification failure. No shell execution. Inventory contains OS/architecture/CPU/hostname and bounded package versions. Agent does not perform vulnerability matching; the API may match reported packages against configured rules. Run with the narrowest privileges and mount only explicitly managed paths. Container operation requires a persistent state volume and explicit target mount.

## Additional collectors
JSON configuration supports `FIMPaths` (at most 100 regular files, 8 MiB each) and `LogPaths` (at most 20 regular files, 16 KiB per cycle). FIM establishes an initial SHA-256/missing baseline, then reports create/delete/modify/unreadable transitions; invalid, oversized or inaccessible targets are reported as unreadable. An initial unreadable target is also reported. Linux log monitoring persists device/inode identity plus offsets/prefix to detect replacement even with an identical prefix. Copy-truncate followed by rewriting an identical prefix beyond the prior size between polls remains indistinguishable. Activity evidence includes counts and hash, never raw log contents. Partial lines are persisted across cycles and restarts, capped at 64 KiB; oversized lines are discarded through their next newline. Collector state commits after durable report enqueue; interrupted commits may replay observations. Persisted per-file transition generations keep FIM IDs stable during replay while distinguishing repeated create/delete cycles.

Linux package inventory uses only fixed dpkg-query/rpm invocations without a shell, bounded to 3 seconds per command, 256 KiB output and 2,000 packages. Linux permission targets use openat/O_NOFOLLOW on each component before descriptor chmod. Remote policy support is described below.

Remote policy is fetched from `/api/agent/policy` each cycle and cached privately for outages. Each successful snapshot replaces prior remote rules. BASELINE and FIM paths must pass the configured AllowedRoot boundary and symlink checks; local configured collectors remain independent. LOG substring rules evaluate complete lines, retaining matching collection timestamps across cycles/restarts. `windowSeconds` is 1–86400 (default 60); threshold counts matching lines in that rolling window and notifications are limited to one per rule/path/window. Source matches the configured log pathname once per complete line. Timestamps reflect collection time, not parsing of embedded log timestamps. Counters persist up to the threshold; no semantic/multi-event correlation is implemented. Package inventory uses objects `{name,version}`.

## Delivery and remediation guarantees
Heartbeat findings are serialized with string evidence and atomically queued in batches of at most 100 before collector cursors advance. Completed or interrupted task results remain in a durable outbox until the API acknowledges them; restart replays results without repeating chmod. The API must accept identical result replay. Remediation accepts only modes 0600, 0640 and 0644. Linux walks every path component through pinned directory descriptors with openat/O_NOFOLLOW and changes the final descriptor. Other operating systems disable remediation. Keep the allowed root controlled by trusted administrators.

## Enrollment recovery
Before enrollment, the Agent persists its identity and a cryptographically random 32-byte recovery credential in the private identity file. The enrollment API must return the same asset/token for a replay with that identity and credential, rejecting mismatched credentials. A lost response can therefore be retried after restart. Enrollment is complete only when both asset ID and token exist. Back up the state directory securely; losing it loses the recovery identity. No tokens or raw log contents are logged.

## CONFIG_VALUE remediation
Linux additionally supports CONFIG_VALUE with `{path,key,expectedValue,value}` for literal line-based KEY=VALUE files only. Keys must match `[A-Za-z_][A-Za-z0-9_]*`; values cannot contain control characters. The target must have exactly one matching key, and its current value must equal expectedValue. Files and results are bounded to 64 KiB and use the same allowed-root and secure descriptor traversal restrictions. A private backup stores the original bytes under a task-derived hashed filename before modification. Writes truncate and fsync, verify exact resulting content and path identity, and attempt rollback on failure. Reports include byte counts and backup filename, not configuration values. No service restart or functional health check occurs; an operator must independently verify application health. A process/power failure during the in-place write can require manual restoration from the backup. Concurrent external writers must be excluded operationally.

Both mutation templates reject files with more than one hardlink before changing them. CONFIG_VALUE preserves the file mode and writes a private `config-recovery.json` marker before its first mutation. If execution stops with that marker present, subsequent cycles fail closed before enrollment, reporting or task polling. An administrator must inspect the recorded backup/path, restore the backup when necessary, independently verify content and application health, then remove the marker to resume. Successful verified writes or successful rollback remove the marker. In-place writes are not atomic and automatic crash restoration is intentionally not attempted.

State-file replacement syncs both the written file and its parent directory after rename. Recovery-marker deletion also syncs the parent directory. Failure to persist the marker aborts configuration mutation. These guarantees depend on the underlying filesystem honoring fsync; container state must reside on persistent storage.

Package inventory includes `packageCollection: {complete, reason}`. Missing/failing package managers, truncated command output, malformed rows and the package-count cap mark collection incomplete. The API must treat absent matches in incomplete inventories as unknown; reported positive matches remain usable. Truncated trailing package rows are discarded.


## Inventory and baseline checks
Linux `/proc/net/{tcp,tcp6,udp,udp6}` provides up to 2,000 listening TCP/unconnected UDP sockets (`ports`, with protocol/address/port/state). `portCollection` reports completeness. `systemctl list-units --type=service --all` provides up to 2,000 active/loaded systemd units, not all installable service definitions. On an actual OpenRC host the current source uses bounded, nonroot `/bin/rc-status --nocolor --format ini --servicelist` output, including stopped services; known states map to the shared active/inactive/failed/transitional states. `serviceCollection` keeps missing commands, timeout, malformed/unknown/duplicate rows, empty output and truncation incomplete. Fixed commands use no shell. Missing procfs or an unsupported service manager does not become a false empty-success inventory.

OpenRC installation is available in the local platform as signed canary `0.4.1`; stable `0.4.0` remains the default. The same source was verified with `0.4.1-rc.9` on Alpine 3.23.4 ARM64 and amd64 in project-owned native VMs. The distinct `0.4.1` ARM64 artifact also passed the actual OpenRC core flow and the representative Ubuntu 24.04 systemd installation, preserving its full profile, identity and exact original units. AMD64 native core evidence is RC9 source-equivalence evidence, not a fresh `0.4.1` whole-binary native run. Both `0.4.1` architecture artifacts and their signed tar.gz/deb/rpm packages were published with exact-byte download verification; no host rollout was created. Both architectures passed online/repeated installation, APK origin inventory, nonroot collector/root executor isolation, actual cgroup limits, signed permission repair with independent verification, and SIGKILL recovery. OpenRC sets `no_new_privs=yes` before exec; the agent requires inherited kernel NoNewPrivileges and native checks inspect every runtime thread. Earlier RC8 process-leader checks did not establish this all-thread property and are superseded. Offline preparation evidence belongs to ARM64 RC2 and amd64 RC8 and is reused explicitly, rather than called a fresh RC9 offline run. The amd64 guest uses software CPU emulation for functional checks only. Remaining failure/uninstall scenarios retain separate acceptance scope. The systemd-only `SERVICE_STATE` remediation below does not imply OpenRC service-state support.

BASELINE supports `type: FILE_PERMISSION` (default), `CONFIG_VALUE` with `path,key,value`, and `SERVICE_STATE` with `service,state` (`active`, `inactive`, `failed`). Files must be inside AllowedRoot, regular, and free of symlink components; literal KEY=VALUE configuration checks reject missing/duplicate keys. Config value evidence is redacted. Service checks use fixed `systemctl show` arguments, a validated name, and a two-second timeout. Inaccessible checks produce a risk with a diagnostic status. FIM can watch an absent file if its existing parent passes AllowedRoot checks.

## Resource budgets and offline behavior
Optional AGENT_CONFIG fields: `MaxCPUs` limits Go execution threads, `MaxMemoryBytes` sets Go's soft memory target, `MaxQueueBytes` limits queued JSON payload bytes, `BytesPerSecond` paces management HTTP request/response payload chunks. Zero preserves defaults. These cooperative controls do not enforce an OS CPU percentage, a total filesystem quota, or network framing overhead; configure OS limits as well. The sample `selfguard-agent.service` provides CPUQuota/MemoryMax and a separate unprivileged account. Adapt explicit managed paths and file permissions before installation. The installation directory stays administrator-owned and read-only to the service (e.g. 0755, or 0750 with the service group). Nonsecret upgrade status is 0644; backups and trust/installation receipts remain private.

When delivery fails, an enrolled Agent continues cached-policy collection into its durable queue. Full queues stop cursor advancement. Heartbeats include `agentDiagnostics` with configured budgets, queue count and the previous delivery result. The client timeout still bounds requests, so low payload rates can cause timeout/retry. Package/service subprocesses keep their own output/time limits. Queue byte accounting covers payloads, not filesystem metadata; private backups/task history have separate existing bounds. No production resource curve or long-duration outage claim is made.

## Signed staged upgrades and rollback
Explicit operator commands, run from a separate trusted updater executable:

```sh
AGENT_CONFIG=/etc/selfguard-agent/config.json /path/to/trusted-updater --stage-upgrade /path/to/envelope.json /path/to/candidate
AGENT_CONFIG=/etc/selfguard-agent/config.json /path/to/trusted-updater --rollback-upgrade
```

Configure `UpgradeInstallRoot` (e.g. `/opt/selfguard-agent`, administrator-owned and not group/world writable) and `UpgradePublicKey` (base64 of the 32-byte Ed25519 public key). The directory must initially contain a regular single-link `current` executable. The updater refuses to overwrite its own running executable; use a separate trusted copy. Normal Agent cycles trigger upgrades only through the explicit opt-in remote rollout configuration described below. Tests use temporary installation directories and never replace any host executable.

The envelope is `{ "manifest": <JSON object>, "signature": "<base64 Ed25519 signature>" }`. Sign the exact JSON bytes of the nested manifest, preserving whitespace when constructing the envelope. Manifest fields: `version`, monotonic positive `sequence`, lowercase hex `sha256`, `size` (1–64 MiB), `os`, `architecture`, and RFC3339 `expiresAt`. Reject invalid signatures/checksums, expired or wrong-target packages, and sequence replay/downgrade. Preserve the configured trust key outside release packages. Key rotation is an operator configuration action; this is not a remote trust-key distribution system.

The updater persists a private backup and recovery marker, fsyncs a staged file, atomically replaces the on-disk `current` slot, reads the bytes back, and runs that executable with `--self-test` (five-second limit). An unsuccessful self-test or installation receipt causes restoration of the old content/mode/receipt. A persistent highest sequence prevents replay even after an explicit rollback. `upgrade-status.json` records `STAGED_PENDING_RESTART` or `ROLLED_BACK_PENDING_RESTART`; heartbeat `upgradeStatus` exposes that status. The running Agent version changes only after the supervisor restarts it; an operator must verify enrollment, policy delivery and application health, and can run the rollback command then restart the supervisor if needed. Self-test checks process viability, not functional health.

An interruption with `upgrade-recovery.json` present refuses further staging until explicit rollback. Upgrades pause Agent cycles when the marker is visible. If backup/restore fails, retain the marker and restore the administrator-controlled backup manually before resuming. Install-state files contain executable backups; protect the installation root. Keep installed receipts/highest sequence during backups and recovery. Fixture-compatible aliases remain available with `UpgradeFixtureRoot` and a `.selfguard-upgrade-fixture` marker containing `offline fixture only\n`; production configuration should use UpgradeInstallRoot.

Example service procedure: create `selfguard-agent` without login, provision `/etc/selfguard-agent/config.json` readable only by that account, create its state directory, grant only the explicitly managed files required for checks/remediation, and install the sample unit after adapting its paths and OS limits. Stage signed releases using an administrator-run separate updater, inspect the receipt/status, restart `selfguard-agent.service`, and independently check diagnostics. The unit intentionally cannot write its installation root. Installation, restart, permissions, and production upgrades are not performed by tests.

Linux inventory includes `distribution: {id, versionId}` from `/etc/os-release` (64 KiB maximum, literal quoted/unquoted values, lowercase ID, no shell interpretation) and `distributionCollection: {complete, reason}`. Missing, ambiguous or malformed fields produce empty distribution fields with incomplete status; consumers must not infer Debian/Ubuntu applicability from the generic `os: linux` field.


## SERVICE_STATE remediation (third constrained template)
Task parameters are `{service, expectedState, state}`. `AllowedServices` is an exact local configuration allowlist, empty by default (service changes disabled). Unit names must match `^[A-Za-z0-9_.@-]+\.service$`, have at most 200 characters, and cannot start with `-`. Expected and desired states must be `active` or `inactive`. Other observed states (failed/activating/etc.) are refused before mutation because they cannot be restored exactly by start/stop. A mismatching expected state fails without change; an already-matching target is a verified no-op.

On Linux the Agent uses only fixed `/usr/bin/systemctl is-active|start|stop -- UNIT` invocations, no shell or PATH-resolved remediation executable. Each call has a three-second timeout and bounded output. This requires systemd at that exact path plus explicitly provisioned OS permission for the service account to control only the managed units; the Agent does not elevate privileges or install broad sudo/Polkit rules. Allowlisting in JSON does not grant OS rights. Stopping a service can interrupt traffic; review business impact before approval and choose a suitable execution window.

Before start/stop, the Agent fsyncs `service-recovery.json` containing task/unit/previous/target state. It then verifies the requested active/inactive state. Any operation or verification failure attempts restoration of the previous state and verifies restoration. Result details include previous/observed/rollback states, rollbackSucceeded, resultUnknown and recoveryRequired. Failed restore or command timeout retains the marker and pauses subsequent Agent cycles; a systemd job may outlive the CLI timeout even if a later probe temporarily appears restored. Result transport has a boolean success field, so consumers must inspect these recovery/unknown details rather than assuming an ordinary failed task is safe to retry.

On interruption or retained recovery marker, an administrator must inspect the recorded unit, actual state and any outstanding systemd job, restore the intended prior state when needed, independently check application health, reconcile the platform task outcome, and only then remove the marker. Never clear it just to retry. Verified success or verified non-timeout rollback removes the marker; independent application health and platform risk verification are still required. ActiveState alone does not prove application health or perform a restart (active→active is a no-op). Tests inject a bounded command runner and use only temporary files; they never start or stop host services. These three templates do not constitute arbitrary patching or unrestricted command execution.

## Opt-in remote signed rollouts

The service can poll controlled releases only when its private configuration explicitly sets `UpgradeInstallRoot`, `UpgradePublicKey` (raw Ed25519 key, base64), and `UpgradeOrigins` (exact HTTPS origins, including a non-default port if needed). The API independently requires `AGENT_UPGRADE_PUBLIC_KEY` and comma-separated `AGENT_UPGRADE_ORIGINS`. Download requests contain no agent credentials, refuse redirects and enforce signed sizes up to 64 MiB, expiry, OS/architecture, checksum and monotonic sequence. The exact signed manifest bytes are transported as base64 `manifestBytes`; `signature` remains base64 Ed25519. Only trusted signed executables run the bounded `--self-test`; failure restores the private local executable backup.

Build each release with its actual version, for example `go build -ldflags '-X main.agentVersion=0.2.0'`. Operators explicitly grant the service account ownership of its private installation root and add that exact root to the unit's `ReadWritePaths` when enabling this mode. The sample unit keeps remote upgrade disabled until configured. Linux can atomically replace the running executable's directory entry; the old process reports STAGED then exits 75. `Restart=on-failure` starts `current`, and only a fresh heartbeat reporting the expected release version permits canary/batch advancement. A candidate that reports a different version is restored from the private executable backup and exits for a supervisor restart. Missing heartbeats or failed targets pause the rollout; operators review and cancel before scheduling a corrected release. No systemd command is remotely supplied or invoked for upgrades.

Administrators register `/api/rollouts` with `manifestBytes`, `signature`, trusted `artifactUrl`, ordered `targetIds`, and `batchSize`; approval at `/:id/approve` must repeat those exact ordered IDs. The first target is the canary. Every target in a later batch must restart and pass the version heartbeat gate before the following batch. `/:id/pause` and `/:id/cancel` stop additional claims. Already claimed operations can still report their final outcome. An interrupted upgrade retaining `upgrade-recovery.json` continues to require administrator reconciliation; do not clear markers to retry blindly.

## Repair readback and authorized rollback

Each mutation records a private local repair plan keyed by the original task ID. `VERIFY_READ` accepts only `{originalTaskId}` and performs a new bounded filesystem/service read; it never trusts the cached mutation result as proof of current state. `ROLLBACK` accepts the same reference, requires a locally recorded successful original task and checks that its applied state still matches before restoring the prior locally recorded mode/config value/service state. A changed target or pending recovery marker is refused. Backup paths, commands and original values cannot be supplied by the remote task. Config and service rollback use the same allowlisted, precondition-checked mutation handlers. The API creates pending rollback tasks for normal approval and fresh readback tasks for independent verification. Application health beyond the selected file/key/service state remains a separate operator check.

By default, collector findings from configured host logs and FIM additionally emit redacted correlation metadata (`HOST_LOG` / `FIM_CHANGE`) to `/api/telemetry/events`. Metadata contains only source category and an optional validated rule ID; no paths, lines, request bodies or secrets. Each event uses a stable SHA256 ID scoped to its enrolled asset and collector external ID. Heartbeat and telemetry batches share one durable queue write and capacity check, so collector cursors advance only after both are safely buffered. Retries preserve IDs for server deduplication.


## Optional redacted log context

`LogIncludeMessage` defaults to `false`. Enabling it adds `HOST_LOG_LINE` telemetry for complete lines from locally configured `LogPaths`; it does not add FIM file contents or change finding evidence. The platform must independently enable its administrator-controlled log-message policy before retaining these messages. Each line event has a stable SHA256 identifier scoped to the enrolled asset, source-file identity, original byte offset and line hash; its data contains only `category: "agent-log"` and `message`. The configured source path contributes to the digest and is not sent as a context field.

Built-in RE2 redactions mask password/token/secret/API-key assignments and Authorization Bearer/Basic credentials, including quoted values. `LogRedactions` adds up to 20 application-specific RE2 expressions, each 1–512 bytes; invalid and empty-matching expressions prevent startup. Matching custom text becomes `[REDACTED]`. Messages are redacted before UTF-8-safe truncation to 4096 bytes. Control characters are replaced with spaces (tabs remain). Excessive replacement expansion suppresses that line's context.

The existing partial-line and rotation handling remains in use. With context enabled, collection processes at most 100 complete lines per configured file per cycle, retaining unread lines behind the durable cursor for subsequent cycles. Heartbeat findings, metadata and line context share the same atomic queue persistence and capacity checks. Cursors advance only after that queue write succeeds, and retries keep stable event IDs for server deduplication. Private partial-line state and enrollment credentials remain in the protected agent state directory.

FILE_PERMISSION and CONFIG_VALUE tasks may include optional `healthService`, naming an exact Linux `.service` unit from the local `AllowedServices` configuration. An unlisted/invalid unit refuses the task before any file mutation. The field is persisted in the private original plan and inherited by rollback. Independent `VERIFY_READ` then combines a fresh file/key check with fixed, bounded `/usr/bin/systemctl is-active -- UNIT`; only `active` passes the related-service gate. The probe never starts, stops or restarts the service. Result details expose the file check, unit, health outcome and `healthVerified`; a timeout/probe error reports `UNKNOWN` and `resultUnknown: "true"`. A read-only probe timeout does not create a service mutation recovery marker. Existing service start/stop recovery markers and timeout handling remain unchanged. This verifies active state, while application-level behavior may need a separate operational check.

## Optional Unix executor privilege separation (Linux)

Configure `ExecutorSocket` in the unprivileged collector's root-owned configuration to delegate every mutation, rollback and readback. Once set, missing signatures/socket failures never fall back to local mutation. Keep the collector account without write access to managed files and without service-control privileges. The separate `--executor` process requires root, a protected root-owned `AGENT_CONFIG`, a root-private `StateDir`, and independently configured `AllowedRoot` / `AllowedServices`. Its configuration must include `ExecutorSocket`, `ExecutorAssetID` (the enrolled collector's asset ID), `ExecutorPublicKey` (raw base64 Ed25519 server task-signing public key), and an explicit numeric `ExecutorAllowedUID` for that collector. The private signing key stays on the API. Provision the enrolled asset ID before enabling the executor.

The collector forwards only the API's `{payload, signature}` authorization and checks its task/asset/parameters/expiry binding. The executor verifies the exact signed JSON bytes, expiry, configured asset identity, template allowlist and independent local path/service limits. The Linux Unix socket additionally checks `SO_PEERCRED` against the configured collector UID. The socket is mode 0660; provision its parent as root-owned/non-writable by the collector and configure its group through the service deployment. Root-private durable receipts prevent duplicate execution: identical retries return the stored result, conflicting reuse of an ID is rejected, and an interrupted operation remains unknown until reconciled. Local original plans/results/recovery markers stay in the executor's private state, supporting signed rollback/readback without exposing backup paths to the collector.

The optional `selfguard-executor.service` and `selfguard-collector.service` samples show separate root/unprivileged processes and filesystem rights. The executor accepts commands only through its UID-checked Unix socket and downloads releases only from configured trusted HTTPS origins; the collector cannot write the installation or managed roots. Adapt configured paths, collector numeric UID/group, managed file ownership, read-only log access and narrowly scoped service permissions before deploying. For remote rollout in this mode, configure the same shared root-owned installation slot on both processes and configure release trust/origins on the executor; the collector delegates staging and has no installation write access. These samples are not installed or started by tests. Tests use root-owned temporary directories and a genuine UID 65534 subprocess: direct mutation is denied, while the correctly signed and UID-authorized socket operation succeeds.

The executor also creates a persistent root-owned 0600 `executor-result-key.bin` inside its private state and signs every result for a valid task authorization, including cached replay results. A root operator can export only its raw base64 public key with `AGENT_CONFIG=/etc/selfguard-agent/executor.json /opt/selfguard-agent/current --executor-public-key`, then register that key on the matching platform asset. Keep the private key and original receipt state through backup/recovery. `details.executorProof` is a JSON string `{payload, signature}`; the signed payload is the exact JSON bytes of `{taskId, assetId, result: {success, evidence, details}}`, with `executorProof` excluded from the nested details. This binds success and readback evidence to the privileged process, preventing the unprivileged collector from forging a healthy result. An asset configured to require proof treats missing/invalid proof as unknown and cannot close a risk from it.


Separated processes support the same controlled remote rollout. The API attaches a short-lived, asset/target-bound signed `UPGRADE` authorization whose parameters exactly bind `artifactUrl`, `manifestBytes` and release `signature`. The executor independently checks that authorization and its local release trust key, trusted HTTPS origins, manifest target/expiry/checksum/sequence and candidate self-test. A globally signed release without a valid task authorization cannot trigger privileged staging. The root-owned shared `current` slot is staged with mode 0755 so the unprivileged collector can execute the validated release; neither process accepts arbitrary installation paths from the command.

The executor signs its staging result, waits for the socket client's acknowledgment, then exits 75 for its supervisor to launch the new `current`. The collector reports STAGED with that proof and exits 75 for its own supervisor. After restart it obtains a fresh signed executor reply; registered-key assets advance only when the proof confirms the expected executor version and a process identity different from the one that staged the release, alongside the collector's fresh version heartbeat. Root private receipts, result key, release backup and recovery markers survive replacement of the binary. A root executor that starts with a version different from its last staged installation restores the private backup and restarts; retained upgrade recovery markers continue to require operator reconciliation.


### Provisioning and verification order

1. Provision a stable unprivileged collector UID/group, root-owned binaries/configuration and shared installation directory, a root-owned socket parent, and separate collector/executor state directories. The executor state must remain root-only 0700; managed-root/config/socket ancestors must not be writable by the collector. The sample units use `/run/selfguard-executor/executor.sock`, `/var/lib/selfguard-executor` and `/var/lib/selfguard-agent` when configured consistently.
2. Enroll the collector to obtain its asset ID. Set that ID as `ExecutorAssetID` in the protected executor configuration, set `ExecutorAllowedUID` to its numeric UID, and independently constrain `AllowedRoot`/`AllowedServices`. Configure the API's Ed25519 task-signing private key on the API and only its public key as `ExecutorPublicKey` on the executor. Configure the separate release public key and trusted HTTPS origins on the executor for upgrades.
3. Export `--executor-public-key` as a root operator and bind that public key to the matching asset through the administrator-controlled `executorPublicKey` field. Do this before approving remediation/upgrade tasks. Never accept a result verification key from an untrusted heartbeat. Changing or restoring a result key requires deliberate administrator rebinding; preserve its private state during ordinary upgrades.
4. Point the collector's `ExecutorSocket` at the root socket and use the same shared `UpgradeInstallRoot` for rollout diagnostics/restart. Its optional release settings should match the configured rollout policy. Start the independently supervised processes with the sample units adapted to the host. The collector remains unable to write the installation or managed files.
5. Verify a signed repair, then its separately authorized `VERIFY_READ`. A successful write remains VERIFYING until fresh root-signed file/key/service checks pass. A configured `healthService` additionally requires an active allowlisted related unit. Rollback is a separate approved task referencing the stored original plan and receives its own independent readback. Timeout/unknown outcomes require reconciliation rather than a success declaration.

### Recovery commands, illustrated with fixture paths

Pause the affected rollout before recovery and stop only the affected fixture/host supervisors through the operator's deployment procedure. Inspect the private recovery marker, recorded backup, API target state and both actual process versions. A separate trusted updater may restore the recorded installation backup; for example, using disposable fixture paths:

```sh
AGENT_CONFIG=/tmp/selfguard-fixture/executor.json /tmp/selfguard-fixture/trusted-updater --rollback-upgrade
AGENT_CONFIG=/tmp/selfguard-fixture/executor.json /tmp/selfguard-fixture/trusted-updater --executor-public-key
/tmp/selfguard-fixture/install/current --self-test
```

The updater must be a separate trusted executable, and the fixture configuration must point only at the disposable fixture installation/state. These examples do not install units or operate a host service. Preserve `highest-sequence.json` to prevent release replay, preserve the executor result key/receipts/plans, and independently verify restored contents and application health before resuming supervisors. Do not delete recovery markers merely to retry; interrupted configuration/service operations need the recorded original state reconciled. A self-test confirms bounded executable viability, while the fresh signed executor result and collector heartbeat establish the actual restarted rollout version.

`CYCLONEDX_1_6` (JSON inventory profile).
No application code, npm scripts, pip commands or JAR programs are executed.
Reads use a rooted directory handle; links, special files and paths outside the
configured root are refused. Each result retains installed version, evidence
path and metadata/artifact SHA-256. Limits: 100 inputs, 10 seconds per cycle,
1 MiB per installed metadata file (8 MiB per lock/SBOM), 32 MiB total metadata, 128 MiB per binary/JAR,

are explicitly reported as coverage gaps. Agent 0.4.0 is required for these

## Host network operations (0.4.9)

The collector advertises traffic-capture-v1 and nginx-onboarding-v1 but keeps its existing unprivileged, read-only boundary. Network operations are finite, separately authorized root CLI operations on Linux:

- --capture-traffic CONFIG OUTPUT_DIR: bind one real interface, no promiscuous membership; filter TCP/UDP ports and optional CIDRs; enforce duration, examined-frame, captured-frame, flow and byte budgets. OUTPUT_DIR must already be a root-owned private 0700 directory. CONFIG must be trusted root-owned JSON. Default retains flow metadata only; encrypted payloads remain opaque. Fragmented IP and IPv6 extension chains are not interpreted as transport headers.
- --publish-traffic SUMMARY: upload only the strictly validated summary using the installed asset identity. PCAP is never uploaded. The platform shows the latest summary in the asset's network section.
- Optional includePayload requires snapLen and 1–24 retentionHours. The PCAP is local/private; --expire-traffic OUTPUT_DIR removes an expired payload. No recurring root cleanup service is silently installed: arrange this command through existing host maintenance before enabling payload capture.
- --onboard-nginx PLAN: use an administrator-generated platform plan to start the fixed-digest, architecture-matching, preloaded self-built WAF image. Docker and nginx must be at the documented trusted paths. It preserves the public Nginx TLS/domain entry and original upstream Host; only one explicit reverse-proxy server/root-location is supported. Complex configs remain unchanged. Actual normal and synthetic-detection records must match before VERIFIED.
- --rollback-nginx TRANSACTION_DIR: restore and test/reload the saved original; refuse to overwrite newer configuration; publish ROLLED_BACK. The local container and private evidence remain for inspection. After confirming restored traffic, stop the owned node and unassign the site in the platform before moving it.

Authorized online installations may select a hostWaf profile. This runs after the Agent's own service/heartbeat acceptance; Agent and Web ingress outcomes remain separate. Offline payload preparation does not grant site takeover. No global WAF credential is distributed: the local node receives its own asset-generation-bound credential and only its assigned site configuration.

## HTTP platform deployments (0.4.10+)

Managed installation accepts an explicit HTTP or HTTPS platform origin. HTTP installations persist `AllowHTTP: true` in collector, executor and recovery connection configuration; manually configured agents can explicitly set `AllowHTTP` or `AGENT_ALLOW_HTTP=true`. This does not enable development mode. HTTPS configuration keeps HTTP disabled, verifies certificate trust, and cannot silently downgrade. HTTP is plaintext and is intended for trusted networks.

The same declared scheme and origin constrain signed upgrade downloads and target-bound download grants; redirects remain disabled. Offline preparation supports both schemes without claiming the platform is online. HTTP platform selection requires Agent 0.4.10 or newer; older releases remain immutable. Host WAF nodes launched from an HTTP installation explicitly receive `WAF_ALLOW_HTTP=true` and require the matching updated WAF image.
